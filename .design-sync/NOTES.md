# design-sync notes — Inkweave

Repo-specific gotchas for syncing this design system to claude.ai/design.
Read this before touching `.design-sync/config.json`.

Project: `Inkweave Design System` — https://claude.ai/design/p/a0ed7aa8-a3a4-4663-bb98-7a13b43de7dc

## The shape of this repo (read first)

**Inkweave is an APP, not a component library.** `apps/web` (`inkweave-web`) has no
`main`, no `module`, no `exports`, and ships no component `dist/`. Everything below
follows from that one fact, and none of it is optional.

- `[GENERAL]` **The bundle entry is a generated barrel.** The storybook shape calls
  `resolveDistEntry` WITHOUT a synth fallback (`package-build.mjs` ~line 237), so with
  no dist it hard-exits `[NO_DIST]`. `.design-sync/entry.tsx` is that entry: one
  `export {X} from '…'` line per storied component, generated by
  `.design-sync/gen-entry.mjs`. **Re-run `node .design-sync/gen-entry.mjs` whenever a
  storied component is added, removed, or renamed** — it is wired as `cfg.buildCmd`, so
  the `resync.mjs` driver runs it automatically; a bare `package-build.mjs` run does not.

- `[GENERAL]` **`extraEntries` is what populates the export gate — do not remove it.**
  Storybook shape keeps only components that are bundle exports
  (`src.components.filter(c => exported.has(c.name))`), and that `exported` set comes
  from a **ts-morph scan of `.d.ts` files**. An app has none, so the first build reported
  `exported PascalCase symbols: 0` and dropped all 164 titles with `[TITLE_UNMAPPED]`.
  Listing the barrel in `cfg.extraEntries` makes the build **source-scan** its
  `export {X} from '…'` lines and add those names to `exported`. Symptom if it regresses:
  a build that finds 164 storybook components and emits 0.

- `[GENERAL]` **`PKG_DIR` is the REPO ROOT, not `apps/web`.** With `--entry`, the build
  walks up from the entry file to the nearest `package.json` with a `name`; from
  `.design-sync/` that is `D:\johnn\Projects\inkweave` (`inkweave`). So every
  PKG_DIR-relative heuristic (`src/`, CSS, docs) misses `apps/web` and must be pinned
  explicitly — hence `cfg.srcDir`, `cfg.cssEntry`. Do NOT "fix" this by moving the
  barrel into `apps/web`: it would land inside the app's tsconfig + ESLint scope and the
  pre-commit/pre-push gates would start linting a generated file.

- `[GENERAL]` **Fonts need `.design-sync/fonts.css` — the compare loop cannot catch this
  one.** `apps/web/src/index.css` declares its five faces with ABSOLUTE urls
  (`url('/fonts/…')`, correct for Vite's `public/`), but the converter resolves
  `@font-face` urls relative to the stylesheet's own directory. All five resolved
  nowhere and were dropped: `_ds_bundle.css fonts: 0 url(s) rewritten, 5 dead
  @font-face block(s) dropped`. Both compare panels then fall back to the SAME chromium
  default, so sheets look like clean matches while every claude.ai/design user gets the
  wrong typography. `.design-sync/fonts.css` re-declares the same five faces with
  repo-relative urls and is wired via `cfg.extraFonts`.
  **Keep it in lockstep with `apps/web/src/index.css`.** This repo sets
  `font-synthesis: none` on `:root`, so a weight with no loaded face does not
  synthesize — it silently renders as the nearest face that exists.

## Fresh-clone setup (local-only, not committed)

Both of these live under gitignored paths, so they must be recreated per clone:

1. **`@types/react` junction at the repo root.** `.d.ts` extraction resolves React
   utility types by walking UP from `PKG_DIR` (the repo root) looking for
   `node_modules/@types/react`; it never descends into `apps/web/node_modules`, and
   pnpm's isolated layout leaves nothing at the root. Without it the build prints
   `[DTS_REACT] @types/react not found` and **every component whose props extend
   `ComponentPropsWithoutRef`/`FC` emits an EMPTY props body** — the design agent then
   codes against a blank API contract. Recreate (PowerShell, no admin needed; update the
   version dir to match `apps/web/node_modules/@types/react`'s realpath):
   ```
   New-Item -ItemType Junction -Path "node_modules\@types\react" `
     -Target "node_modules\.pnpm\@types+react@19.2.17\node_modules\@types\react"
   ```
2. The converter deps: `cd .ds-sync && npm i esbuild ts-morph @types/react playwright &&
   npx playwright install chromium` (see the storybook sub-skill §2.4).

## The two module-identity traps (both were global, both looked like app bugs)

Previews redirect component imports to the shipped bundle, but anything else a story
imports is bundled a SECOND time from source. When that second copy is a **provider**,
the story mounts provider-instance-B while the component reads context-instance-A —
which is null — so the component throws its own "must be used within a Provider" error
**even though the story visibly wraps it**. Do not chase these per-component; they are
always config.

- `[GENERAL]` **react-router.** 17 of 20 render errors on the first clean build were
  `useLocation()/useNavigate() may be used only in the context of a <Router>` and
  `Cannot destructure property 'basename'`, on components whose stories plainly wrap them
  in `<MemoryRouter>`. Fixed by adding `react-router-dom` to `cfg.extraEntries` (rule 1:
  extraEntries imports resolve to the global), collapsing both sides onto one instance.
- `[GENERAL]` **App contexts.** Same failure for `SessionProvider` etc.
  `.design-sync/providers.tsx` re-exports them onto the global and
  `cfg.storyImports.shim` forces story imports of `shared/contexts/` to resolve there.

## `cfg.provider` is mandatory here — the card scaffold is light-themed

`[GENERAL]` The generated card HTML hard-codes `body{margin:0;padding:24px;background:#fff}`
in an inline `<style>` that comes AFTER the stylesheet links, so it beats the bundle's own
`body{background:#0d0d14}`. **Every preview rendered on WHITE** — on a dark-fantasy system
that inverts the whole palette, and it would reach every design the agent builds. The
scaffold is app-contract surface (never fork `emit.mjs`), so the fix is
`cfg.provider: {"component": "InkweaveDesignRoot"}` — a wrapper in
`.design-sync/providers.tsx` that re-establishes the dark surface inside the mount,
mirroring the decorator in `.storybook/preview.tsx`.

Note it deliberately drops that decorator's `minHeight: 100vh`: storybook renders
fullscreen, but the preview mount sits in a grid cell, and a viewport-tall wrapper would
stretch every cell in the product card.

**Do not "simplify" this away by trusting `body{background}` from `index.css`.** That rule
does ship (it is in `_ds_bundle.css`), it just loses to the scaffold's inline style.

### Portalled scrims read grey — known, accepted, do not re-litigate

Overlay backdrops (`FilterDialog`, `DialogShell`, `BottomSheet`, the 16 `cardMode: single`
components) render **grey** in previews where storybook shows near-black. The dialog panel
itself matches exactly; only the scrim tone differs.

Cause: these overlays portal to `document.body`, which is OUTSIDE the provider tree, so
their `position: fixed` scrim composites over the scaffold's white body. Nothing in
`cfg.provider` can reach a portal, and `emit.mjs` (which owns that white body) is
app-contract surface that must never be forked.

`InkweaveDesignRoot` does set `transform: translateZ(0)` — a containing block for
**in-tree** fixed descendants, which is genuinely useful — but **it was measured and it did
NOT fix the portalled case.** Don't re-try it expecting a different result.

This is cosmetic to the preview card only: in a real design the scrim overlays the
design's own dark page, so the shipped component is correct. Grade these `close` with a
note, per the rubric's acceptance bar.

`cfg.provider.inner` is `SessionProvider`. Storybook does NOT provide it globally, so
`AboutPage`, `LegalPage`, `PrivacyPage`, `TermsPage`, `DisclaimerPage`, `AuthButton` and
`SignInDialog` are `sb-error` in the reference (`useSession must be used within a
SessionProvider`) while the PREVIEW renders them correctly. That is deliberate: the
preview renders MORE than the gated reference, so grade those components on their own
merit and do not read the difference as a preview defect. Supplying it is safe —
`SessionProvider` no-ops when Supabase env is unset (`getSupabase() === null` →
`enabled: false`, no network, resolves immediately).

## `guidelinesGlob` is a SECURITY control here — do not widen it casually

The default guidelines sweep picked up **`docs/SECURITY_AUDIT.md`** and staged it for
upload to the Claude Design project. That file is gitignored precisely because it is
sensitive ("Security audit findings — sensitive, keep out of the public repo") and is
untracked in git — uploading it would have published it to a shareable project.

Why the built-in guard missed it: the converter excludes repo-meta docs with
`/^(CHANGELOG|…|SECURITY|…)\b/i`, but `_` is a **word character**, so `SECURITY_AUDIT.md`
never matches `SECURITY\b`. The default exclusion is a prefix-with-word-boundary test, and
an underscore defeats it.

`cfg.guidelinesGlob` is therefore pinned to an explicit allowlist of design-relevant docs
(`UX_REFERENCE`, `UX_AUDIT`, `TECH_STACK`, `DESIGN_SYSTEM_MIRROR`). **Treat it as an
allowlist, not a convenience filter.** Before adding an entry, ask whether that document
should be readable by anyone the project is shared with. Deliberately excluded as internal
rather than sensitive: `DATABASE.md`, `CARD_DATA_PIPELINE.md`, `PREVIEW_CARD_PARSER.md`,
`SYNERGY_AUDIT.md`, `V1_LAUNCH_PLAN.md`.

## Real prop contracts come from a declaration emit (`tsconfig.dts.json`)

161 of 168 components declare their `*Props` interface WITHOUT exporting it — that is the
repo's convention. With no `.d.ts` tree, the extractor fell back to `[key: string]: unknown`
for every component, i.e. no API contract at all for the design agent.

`.design-sync/tsconfig.dts.json` fixes this: it extends `apps/web/tsconfig.app.json` with
`emitDeclarationOnly` into `<repo-root>/dist/types` (already gitignored), which
`findTypesRoot` discovers via its `dist/types` probe. Props then arrive complete, with
their JSDoc. It is wired into `cfg.buildCmd`, so the driver re-emits automatically.
`"types": []` is required in that tsconfig — otherwise `vite/client` resolves relative to
`.design-sync/` and tsc exits 1 (it still emits, so the failure is easy to miss).

Known cosmetic gap: 15 emitted `.d.ts` reference a bare `CSSProperties` (`style?:
CSSProperties`) while importing only `* as React`, so that name does not resolve — the
extractor flattens the props body without carrying the source's
`import type {CSSProperties} from 'react'`. `package-validate` passes because it parses
rather than type-checks. Left as-is deliberately: intent is still legible to the agent, and
the alternative is 15 hand-written `cfg.dtsPropsFor` bodies that would then rot.

## Grading technique: the shrunk contact sheet LIES about small elements

`[GENERAL]` The sheet scales the two panels by very different factors (a ~76px-wide
storybook shot beside a ~900px-wide preview shot), and the perceived brightness/saturation
of a sub-20px element changes with the scale factor. This produced two false defects in
wave 1: `IconButton/Disabled` looked like it had lost its `opacity: 0.4`, and
`StrengthBadge/Small` looked like it had a brighter green fill. **Both were byte-identical**
— disabled `rgb(65,72,79)` vs enabled `rgb(144,161,169)` on both sides, fill `rgb(26,61,26)`
on both sides.

For small glyphs, badges and swatches: open the full-res `raw/*__sb.png` / `*__ds.png` pair,
and when still unsure sample the actual pixels with a playwright + canvas `getImageData`
probe. Two gotchas if you write that probe: run it from `.ds-sync/` (playwright is only
installed there), and load the PNG as a `data:` URL — a `file://` image on an `about:blank`
page fails `decode()` with `EncodingError`.

## Two accepted preview artifacts (deliberate, do not "fix" per component)

- `[GENERAL]` **Full-viewport (`100vh`) components sit 40px low and clip bottom-anchored
  content.** The mount is inset by 24px (`emit.mjs` scaffold `body{padding:24px}`, unforkable)
  plus 16px (`InkweaveDesignRoot` padding), so a 700px-tall `<main>` spans y40..y740 and
  `bottom`-anchored content lands off-screen — `FullPageNotice` loses its own `INKWEAVE`
  watermark, and the `src/pages/*` components render the same way. **The fix is to set
  `InkweaveDesignRoot`'s `padding` to 0**, which also matches the storybook decorator exactly
  (it uses `padding: 0`). Not applied in the first sync: `provider` is in the grade contract,
  so it clears every earned grade. **Apply it at the START of the next sync, before any
  grading.**
- `[GENERAL]` **`parameters: {layout: 'centered'}` is not replicated.** The generated preview
  wrapper composes `meta.decorators` + `story.render` but ignores `parameters.layout`, so a
  story whose decorator has a VISIBLE background (e.g. `Tooltip`'s `#1a1a2e` padded box)
  shows that box shrink-wrapped in storybook and full-panel-width in the preview. The
  component under test is byte-identical. Grade `match` per the rubric's framing clause.

## Storybook

- `.storybook` lives at `apps/web/.storybook`, NOT the repo root (`cfg.storybookConfigDir`).
- Build the reference with `pnpm exec storybook build` from `apps/web`, with `-o` as a
  **repo-root** path, never the repo's own `build-storybook` script:
  `pnpm exec storybook build -c apps/web/.storybook -o <repo-root>/.design-sync/sb-reference`
- The global decorator in `.storybook/preview.tsx` only wraps stories in a `#0d0d14`
  background div — but **`cfg.provider` is still required** to reproduce it (see
  "`cfg.provider` is mandatory here"). `body { background: #0d0d14 }` does ship via
  `cfg.cssEntry`, yet the card scaffold's inline `body{…background:#fff}` beats it.
- The decorator bundle FAILS on this repo (`Could not resolve "/fonts/marcellus-400.woff2"`,
  because `preview.tsx` imports `index.css` whose font urls are absolute). Harmless: setting
  `cfg.provider` skips decorator bundling entirely, which is what we do.
- Per-story providers (`CardDataProvider`, `SessionProvider`, `CardModalProvider`,
  routers) live in the individual story files' `decorators`, and previews compile the
  story module whole — so they come along automatically. 82 of 167 story files have
  their own decorators.

## The reference storybook is built WITH `apps/web/.env.local` — build it without

`[GENERAL]` `pnpm exec storybook build` runs from `apps/web`, so Vite loads `.env.local` and
inlines the real `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` into the reference bundle.
Two consequences:

1. **Supabase-backed components render LIVE data in the reference and their degraded path in
   the preview**, which reads as a preview defect and is not one. `CommunityColumn` shows a
   populated column (9.0/10, "5 VOTES") in the reference vs the "Not enough votes yet" empty
   state in the preview; `EngineColumn` gains a whole community-distribution block with live
   Fair 86% / Higher 14% numbers. Gates: `useQuickVote.ts` (`getSupabase() !== null` →
   `state: 'hidden'`) and `usePairScore`. Graded `close` with the cause recorded.
   `CommunityColumn.stories.tsx`'s own decorator comment says the intended snapshot IS the
   empty state — so the reference has silently stopped matching its story's stated intent.
2. **The reference is non-deterministic** — it depends on live vote counts that change
   between runs.

**Fix for the next sync: build `sb-reference` with the Supabase env unset** (this repo's
recurring `.env.local`-leaks-into-a-test-harness trap — same class as the vitest one).

**Security — verified, no leak.** The credentials reach `.design-sync/sb-reference/assets/
SessionContext-*.js` ONLY, which is gitignored and never uploaded. `ds-bundle/` contains no
project ref (`ttyidjyaxnycbpxwngqr`) and no JWT-shaped token; its only Supabase strings are
supabase-js's own doc examples (`example.supabase.co`) and the env VARIABLE names. Re-verify
with: `grep -rl "ttyidjyaxnycbpxwngqr" ds-bundle` and
`grep -rlE "eyJ[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}" ds-bundle` — both must be empty.

## `skeleton.css` is missing from the bundle — EVERY loading state renders as nothing

`[GENERAL]` **The highest-impact defect found in the first sync, and it is not preview-only.**
`react-loading-skeleton/dist/skeleton.css` is imported by `apps/web/src/main.tsx` and by
`.storybook/preview.tsx`, but NOT by `cfg.cssEntry` (`apps/web/src/index.css`) — so
`_ds_bundle.css` carries no `.react-loading-skeleton` rule at all. That class supplies
`background-color: var(--base-color, #ebebeb)`, `width: 100%`, `display: inline-flex` and the
`::after` shimmer; without it every `<Skeleton>` is a zero-size, background-less inline span.

Symptom: the preview is an empty dark panel with `error: 0`, so it reads as a silent
no-render rather than a CSS gap. Affects `CardDetailSkeleton`, `CardGridSkeleton`,
`DeckListSkeleton`, `DeckViewSkeleton`, `HomePageSkeleton`. `HomePageSkeleton` is the proof
case: its logo, subtitle and featured row match exactly and ONLY the four `<Skeleton>` bars
vanish. `FeaturedCardsSkeleton` is unaffected because its shimmer comes from `index.css`'s
own `.inkweave-shimmer-tile`, which does ship.

**The same `_ds_bundle.css` goes to claude.ai/design, so every loading state the design agent
builds renders as nothing.** Fix (config, not preview): `cfg.cssEntry` takes a single path —
point it at a small wrapper stylesheet that `@import`s
`react-loading-skeleton/dist/skeleton.css` **before** `apps/web/src/index.css`, or add that
`@import` to `index.css` itself (mirroring what `main.tsx` already does at runtime).
**Cheap to apply: CSS is in the styling slice, not the grade contract, so grades carry.**
Not applied in the first sync only because any rebuild would have pulled in uncommitted app
work (see "Working-tree drift").

## `CardGrid` hangs the capture, like `CardTile`

`CardGrid` renders 12–30 `CardTile`s per story, and `CardTile` is the known storybook-page
crasher — so `CardGrid` stalls any run it is queued in front of (10+ min in a batch, 7+ min
solo, zero output both times). It needs the same treatment as `CardTile`. **Put neither in a
shared batch**: they block every component queued behind them.

With no sandbox egress, BOTH panels fall back to the ink-coloured `CostFallback`, so the

## The preview server has ONE static root — `/art/**` 404s (a PRODUCT gap, not just a preview one)

`[GENERAL]` `compare.mjs` serves only `ds-bundle`; `apps/web/.storybook/main.ts` mounts the
app's `public/` via `staticDirs`. Components requesting **root-relative** public assets
therefore render in storybook and 404 in the preview. `DeckSummaryCard` is the clear case:
`frameFor()` (`deckFrame.ts`) returns `/art/frames/<slug>.webp`, and those 21 files (172 KB)
exist on disk. `RevealHero`, `RevealsPromoCard` and `SynergyBanner` use `/art/` too.

**This is not the stale-content-hash non-defect** — do not misfile it. The tell: a stale hash
404s on BOTH panels (so `No Art` looks identical to `Two Inks`), whereas the frame webp
loads in exactly ONE panel. Grading `DeckSummaryCard` as "known stale hash" would have buried
a real defect.

**It matters beyond the harness:** the design agent's own pages issue the same root-relative
request, so every deck card it builds gets a broken-image box unless the assets ship. Fixing
it bundle-side (ship `art/**` at the project root, or inline the frames as data URIs) fixes
the product AND the preview; a second static root would fix only the preview. Deferred in the
first sync because `art/**` is not in the approved upload plan. Minor related bug:
`http-serve.mjs`'s MIME table has no `.webp`/`.avif`/`.jpg` entry.

## Working-tree drift (first sync, 2026-08-11) — why this sync has no final driver receipt

**Resolved by the end of the run** — the Phase C work was committed as `fd4ff3cb`,
`a5309a5e`, `08c0a596` while the sync was still going, so the tree is clean again and the
next sync can rebuild freely. What follows is why THIS sync stopped where it did.

The tree was clean when the sync started and did NOT stay clean: in-flight **#553 Phase C**
work (collection binder) landed mid-run — `AppLayout.tsx`, `CardGrid.tsx`,
`cards/loader.ts`, `BrowsePage.tsx`, `collection/index.ts`, `check-story-coverage.mjs`, plus
new untracked `BrowseModeBar.tsx` / `CollectionBinder.tsx` / `CollectionBinderSection.tsx` /
`CollectionCardsContext.tsx` — and `theme.ts` gained `cardGridMinWidthMobile: 140 → 96`
(owner ruling) at 13:40.

Timeline that matters: **sb-reference built 12:29, bundle built 13:35, theme edit 13:40.**
Compare therefore printed `[REFERENCE_STALE?]` for the whole campaign. **Owner ruling: keep
the 12:29 reference and sync the committed design** rather than rebuild.

Two consequences, both deliberate:

1. **No further full rebuilds were run after 13:35.** A rebuild reads the WORKING TREE, so it
   would have pulled unfinished binder work into the design system. That is why the
   `CountBadge.skip` and the `InkweaveDesignRoot` padding fix are documented-but-unapplied
   rather than fixed in place — both need a rebuild.
2. **The §4d driver receipt (`resync.mjs`) was NOT run**, for the same reason: its first
   stage is a build. So this sync has no `.resync-verdict.json` and no refreshed
   `_ds_sync.json` anchor from a receipted build.

**What the next sync must do first**, in this order, from a clean tree:
`node .design-sync/gen-entry.mjs` → the dts emit → full `package-build.mjs` → rebuild
`sb-reference` → then grade. Expect a full re-verify: with no trustworthy anchor, nothing
carries forward, which is the correct and safe outcome.
